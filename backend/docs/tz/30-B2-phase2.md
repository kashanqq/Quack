## 2. Требования, вехи, конфликты — `app/roadmap/`

Чистый пакет: без I/O, без импортов `app.db`, `app.graph`, `app.llm`, `app.agents`. Входы — модели из `app.schemas`, выходы — `app.schemas.roadmap`. Проверяет `tests/test_layers.py` (B3).

### 2.1 `requirements.py` — product-logic §4.1, дельта §3.3

`build_requirements(saved, profile, exam_formats, test_dates, forecasts) -> list[ExamRequirementOut]`:

- Экзамены — объединение `Requirement{type: exam_score}.exam_id` по сохранённым программам. Программа без `exam_score` — не создаёт требования. Экзамен без формата в `exam_formats` — `has_knowledge_model=False`, только вехи (SAT R&W, IELTS и обязательные блоки ЕНТ — если появятся в данных; пока их нет, ветка должна работать на пустом формате).
- `target_score` = максимальный `threshold` по программам; `target_source="programs"`. Если в анкете `academics.sat_target` (или целевой ЕНТ) со `mark="stated"` — он, `target_source="manual"`, даже если ниже порога (ученик решил сам; product-logic §4.1: «можно изменить»).
- `program_ids` — кому нужен, по убыванию порога. `test_dates` — кандидаты после сегодня из календаря экзамена, максимум 3.
- `current_estimate` — `forecast.predicted_scaled` при `coverage ≥ params.c_cov` (`estimate_note="по модели знаний"`), иначе `academics.sat_score / ent_trial_score` («по твоей оценке»), иначе `None` («нет данных»). `params: KnowledgeParams` — последний аргумент (дельта §7.3).

### 2.2 `milestones.py` — product-logic §4.1

`build_milestones(saved, requirements, test_dates, calendars, marks, today) -> list[MilestoneOut]`, `key` по дельте §4.1:

- `registration` и `test` — из ближайших `TestDate` каждого требуемого экзамена (первая дата после сегодня и, если есть, следующая); `late_deadline` — отдельная веха `registration` с `title` «поздняя регистрация».
- `application` — каждый `Deadline{kind: application}` сохранённых программ; `scholarship`, `document` (`kind: other` с текстом), `exam_registration` из программ → `registration` с `program_id`.
- `window` — окно подготовки для экзамена без модели знаний: от сегодня до тест-даты.
- `source` — из `Deadline.source / checked_at / is_demo` или `TestDate`. `done` — ключ в `marks`. Сортировка по дате; прошедшие невыполненные остаются (ученик видит, что пропустил), прошедшие выполненные — в конец.

### 2.3 `conflicts.py` — product-logic §3.5

`find_conflicts(milestones, saved, planned_test_dates) -> list[ConflictOut]` — три правила, каждое с `text` и `options` (варианты разрешения словами, без расчётов темпа — это Ф4):

- `same_day_applications` — две `application` с `document`-требованиями (`Requirement{type: document}`) в один день.
- `exclusive_rounds` — `Deadline.round` содержит `early` у двух программ с одинаковой датой раунда и `Requirement{type: other}` с текстом «binding»/«обязательство» — эвристика по данным пола; если в поле нет таких программ, правило существует и покрыто тестом на фикстуре.
- `exam_after_deadline` — планируемая дата экзамена (`planned_test_dates[exam]`: `academics.sat_date` или первая тест-дата из требований) позже `application`-дедлайна программы, которой этот экзамен нужен. Это тот самый «SAT 7 ноября не успевает к early-подаче МИТ 1 ноября».

### 2.4 `progress.py` — product-logic §4.1

`exam_progress(requirement, states, forecast, milestones) -> ExamProgress`: `readiness` — закрытая потребность к общей: `Σ weight·min(p_recall, p_target) / Σ weight·p_target` по `SkillStateView` (`weight` и `p_target` в модели есть, дельта §6); навыки `low_data` считаются по `p_recall` приора; `milestones_done/total` по экзамену.

### 2.5 Слова

Тексты в `ConflictOut.text`, `MilestoneOut.title`, `estimate_note` — русские, короткие, как в примерах product-logic («Конфликт: SAT 7 ноября не успевает к early-подаче МИТ 1 ноября»). Никаких процентов.

## 3. Датасет

### 3.1 Генератор — `scripts/gen_templates.py`, `app/agents/prompts/gen_template_v1.md`

Полная версия после каркаса из §0.1: промпт получает навык (id, название, описание), формат экзамена (типы, сложности), заблуждения области с описаниями, 2 примера существующих шаблонов как образец формата, и просит N шаблонов разных структур, где каждый дистрактор привязан к заблуждению, а `solution` — по шагам. Выход — `list[TaskTemplateSpec]` structured. Скрипт: прогон `validate_template` на 50 сидах, отброс невалидных с причиной, запись валидных, `--coverage` после. Ретрай один раз на невалидный structured (как в §4.2 tech-stack). Rate-limit — общий бакет `bulk` в Redis, скрипт его уважает (иначе живой чат B3/фронта ляжет).

Ручная проверка обязательна: каждый сгенерированный шаблон открывается глазами по чек-листу product-logic §5.4 (условие однозначно, ответ верен, дистракторы правдоподобны и привязаны к заблуждению, решение по шагам). Формат JSON не меняется; отметка о проверке — список проверенных `id` в `docs/tz/phase2/checklists/templates-ent.md`. Непроверенный шаблон в `main` не попадает.

### 3.2 Шаблоны ЕНТ — `data/templates/ent/<area3>/`

Все 6 областей, 25 навыков, по 2–3 шаблона на навык (~60–75), типы по `ent_math.json` формату (mcq5 в основном, numeric где уместно), сложность по долям секции. Общие навыки `math.*` — шаблоны с `exam_id: ENT_MATH` лежат у тебя, с `SAT_MATH` — у B1; один навык, разные экзамены, разные условия (product-logic: ЕНТ — русскоязычные формулировки НЦТ).

### 3.3 Библиотека заблуждений ЕНТ — `data/misconceptions/ent_*.json`

После первого пуша B1 (каталог вместо файла): по файлу на область ЕНТ, 2–4 заблуждения на область, `error_class`, `skill_ids` на навыки ЕНТ. Ссылки из шаблонов на заблуждения SAT-областей (`alg.json` и др.) — через sync-log к B1.

### 3.4 Библиотека для репетитора

Ты владелец формулировок ловушек для Ф3: для каждого заблуждения обоих экзаменов проверь, что `description` — это то, что репетитор сможет сказать ученику словами (не «ошибка типа A»). Правки в файлах B1/B3 — через sync-log списком, не PR.
