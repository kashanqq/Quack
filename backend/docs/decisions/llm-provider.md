# Решение: провайдер LLM

Статус: принято

## Решение

Провайдер — **Together AI**, OpenAI-совместимый эндпоинт, платный
(кредиты на личном ключе), вместо free tier из tech-stack §4.1.
Два слота — разные модели: быстрая без рассуждений на живой чат,
рассуждающая на фон.

| | Значение |
| :---- | :---- |
| `LLM_BASE_URL` | `https://api.together.xyz/v1` |
| `MODEL_CHAT` | `deepseek-ai/DeepSeek-V4-Flash-0731` |
| `MODEL_BULK` | `deepseek-ai/DeepSeek-V4-Pro-0813` |
| `LLM_STRUCTURED_MODE` | `response_format` |
| `LLM_STRICT_SCHEMA` | `0` |
| `LLM_REASONING_CHAT` | `low` |
| `LLM_REASONING_BULK` | `high` |
| `LLM_TIMEOUT_CHAT_S` | `60` |
| `LLM_TIMEOUT_BULK_S` | `90` |
| `LLM_RPM_CHAT` | `10` — консервативный стартовый предохранитель для собственного rate-limiter в Redis (ТЗ §3.3), не отражение официального лимита провайдера, см. «Результаты пробы» п.3 |
| `LLM_RPM_BULK` | `5` — та же логика, см. «Результаты пробы» п.3 |

Ключ — один на команду, лежит в `.env` на VPS, в репозиторий не
коммитится. Бакет rate-limit в Redis общий для API и воркеров
(ТЗ §3.3): лимит аккаунта общий, и очередь bulk не должна съесть
его во время живого чата.

## Отклонение от бюджета

tech-stack §4.1 предполагает нулевой бюджет и free tier. Решение
его нарушает осознанно: бесплатные тиры Gemini и OpenRouter дают
непредсказуемые задержки и дневные потолки, срыв которых на защите
неустраним. Остаток кредитов на ключе — **не проверено** (нет
доступа к личному кабинету Together из среды агента, только к API
по ключу); проверяется вручную на `api.together.ai` → Billing.
Сама проба 18.09.2026 (три прогона `structured()` на трёх фрагментах
— два в `response_format`, один в `tool` — плюс два прогона
`stream()` с `get_time` и их продолжениями) — по прайсу из таблицы
кандидатов ниже порядка **сотых–первых десятых доллара**, то есть
пренебрежимо мала. Оценка расхода на весь хакатон — **не сделана**:
нет плана нагрузки (сколько сообщений в чате и наблюдений на
ученика), считать не от чего. Порог тревоги: половина остатка →
переключаемся на фоллбек ниже (сам остаток тоже пока не проверен,
см. выше — порог нечем измерить до похода в биллинг).

### Почему не Kimi K3 основным

Модель сильнее выбранных, но в слот `chat` не годится по двум
причинам: выход $15 за 1M при включённых по умолчанию рассуждениях
даёт порядка $0.05–0.10 за реплику, и первый токен приходит после
всего блока размышлений — чек-лист §6 п.2 требует < 3 с. В слоте
`bulk` разница в качестве не окупает 4-кратной цены против V4-Pro
на задаче наблюдателя.

Остаётся как опцион: если на репетиции защиты V4-Pro ошибается в
`skill_id`, `MODEL_BULK` меняется на `moonshotai/Kimi-K3` одной
строкой в `.env`, перезапуск воркеров. Архитектура слотовая, кода
это не трогает.

## Результаты пробы

Скрипт `scripts/llm_probe.py`, прогон 18.09.2026, живой ключ. Прогнан
трижды: дважды в `LLM_STRUCTURED_MODE=response_format` (первый раз —
проверка, что скрипт вообще работает, вывод потерялся в кодировке
консоли; второй — с перенаправлением вывода в файл ради читаемого
русского текста, это и есть канонический прогон ниже) и один раз в
`LLM_STRUCTURED_MODE=tool` для чек-листа п.3. Три прогона вместо
одного — перерасход против «ровно один прогон», порядка того же
порядка величины по деньгам (см. «Отклонение от бюджета»), не
превышает бюджет пробы.

### 1. `structured()` с `ObservationOut`

Три фрагмента чата подготовки на русском, 4–6 реплик, в каждом одно
присланное решение с ошибкой (тексты фрагментов — в самом скрипте).
Список допустимых `skill_id`, переданный модели: `sat.alg.abs_value_eq`,
`sat.alg.linear_eq`, `sat.alg.linear_ineq`, `sat.alg.quadratic_roots`,
`sat.alg.systems_of_eq`, `sat.arith.percent_change`,
`sat.geom.circle_chord`, `sat.stat.mean_median`.

**Режим `response_format` (канонический прогон):**

| Фрагмент | Модель | Валидный JSON с 1-го раза | Наблюдений | `skill_id` из списка |
| :---- | :---- | :---- | :---- | :---- |
| 1 — `sat.alg.abs_value_eq` | V4-Pro | нет (спасено вторым запросом с сообщением о провале валидации) | 7 | да |
| 2 — `sat.alg.quadratic_roots` | V4-Pro | да | 3 | да |
| 3 — `sat.arith.percent_change` | V4-Pro | да | 2 | да |

Итого валидны с первого раза: **2 из 3** (первый пробный прогон,
до перенаправления вывода в файл, дал 3 из 3 — вариативность между
живыми вызовами одной и той же модели, ожидаемо).

**Режим `LLM_STRUCTURED_MODE=tool` (чек-лист §6 п.3):**

| Фрагмент | Модель | Валидный JSON с 1-го раза | Наблюдений | `skill_id` из списка |
| :---- | :---- | :---- | :---- | :---- |
| 1 — `sat.alg.abs_value_eq` | V4-Pro | нет (спасено вторым запросом) | 5 | да |
| 2 — `sat.alg.quadratic_roots` | V4-Pro | да | 3 | да |
| 3 — `sat.arith.percent_change` | V4-Pro | да | 2 | да |

Итого валидны с первого раза: **2 из 3**.

Критерий приёмки: ≥ 2 из 3 валидны с первого раза, `skill_id` только
из переданного списка. **Пройден в обоих режимах.** Ни один прогон не
упал на 400 — лестница «плоская схема → `LLM_STRUCTURED_MODE=tool`»
из-за 400 не понадобилась (`tool` проверен отдельно всё равно, ради
чек-листа §6 п.3, и тоже работает).

### 2. `stream()` с инструментом `get_time`

| Модель | Инструмент вызван | Текст после вызова | Время до 1-го `text_delta` |
| :---- | :---- | :---- | :---- |
| V4-Flash, `effort=low` (прогон в `response_format`) | да | да | **12.98 с** |
| V4-Flash, `effort=low` (прогон в `tool`) | да | да | **14.59 с** |

Критерий: < 3 с. **Не пройден** — оба прогона на порядок медленнее.
Важная оговорка о методике: стандартный протокол tool-calling не
даёт тексту появиться в том же потоке, что и вызов инструмента (ход
модели заканчивается на `tool_calls`, ждёт ответа `role="tool"`), так
что «текст после вызова» здесь — это второй, отдельный вызов
`stream()` с синтетическим результатом `get_time`, а измеренное время
— от начала первого вызова до первого `text_delta`, включая оба
круга модели. Это честная модель полного круга «спросили → инструмент
→ ответ» (то, что увидит ученик в Ф2 при живом инструменте), но не
прямое измерение «печатает ли модель быстро», которое было бы короче
без инструмента вовсе. В Ф1 `router.run_chat` инструменты вообще не
передаёт (эхо-режим), так что этот риск сейчас не блокирует приёмку
§7 фазы 1 — но стоит перепроверить перед тем, как в Ф2 репетитор
начнёт дёргать инструменты в реальном цикле (`run_tool_loop`).

### 3. Лимиты аккаунта

Together отказались от фиксированных Build Tier лимитов. Факт
(проверено 18.09.2026, docs.together.ai/docs/serverless/rate-limits),
цитата из их доков: «Build Tiers (Build Tier 1–5), Scale, and
Enterprise tier labels have been retired. They no longer appear in
your account or API responses.» Лимиты теперь динамические,
per-model, растут с успешным трафиком; фиксированной цифры в
дашборде или в доках больше нет — актуальное значение видно только
в заголовках ответа реального API-запроса: `x-ratelimit-limit`,
`x-ratelimit-remaining`, `x-ratelimit-reset`.

`LLM_RPM_CHAT=10` и `LLM_RPM_BULK=5` — это не оценка официального
лимита провайдера (его в фиксированном виде не существует), а
консервативный стартовый предохранитель для нашего собственного
rate-limiter в Redis (ТЗ §3.3 B2). Наш circuit breaker (§3.4)
реагирует на реальный `429` от провайдера, а не на предсказанное
число, поэтому отсутствие фиксированного лимита у Together
архитектурно не проблема.

## Что не работает и как обходится

**Рассуждения приходят отдельным полем чанка, не в `delta.content`.**
Клиент (§3.2) поле распознаёт и **выбрасывает**, не склеивая с
текстом. Если склеить — внутренний монолог попадёт в `text_full`,
оттуда в историю сообщений и в окно наблюдателя, а `check_facts`
начнёт ловить числа из черновых прикидок модели и валить
постпроверку. Показ рассуждений пользователю в Ф1 не делаем:
`StreamEvent` — общий контракт (`00-contracts.md`), новый тип
события тянет за собой SSE-транспорт, запись событий и фронт.

**Рассуждения репетитора показывать нельзя и дальше.** В блоке
размышлений модель решает задачу целиком до того, как придумает
подсказку. Открытый спойлер = выданный ответ, механика уровней
подсказки ломается. Если в Ф3 добавляем `ReasoningDelta` — только
для чата подбора, там скрывать нечего.

**`reasoning_effort` не предусмотрен интерфейсом `LLMClient`.**
Добавлен маппинг слот → effort в `__init__`, подставляется в
`chat.completions.create` рядом с моделью и таймаутом. Две новые
переменные `LLM_REASONING_CHAT`, `LLM_REASONING_BULK`.

**`LLM_TIMEOUT_BULK_S` поднят с 30 до 90.** Дефолт из
`00-contracts.md` рассчитан на модель без рассуждений; V4-Pro с
`effort=high` на длинном окне в 30 с не укладывается, и таймауты
ложно открывают circuit breaker.

**`strict: true` в `json_schema` не используется** (`LLM_STRICT_SCHEMA=0`).
Риск: `model_json_schema()` от Pydantic для полей `str | None`
генерирует `anyOf` и `$defs`, и часть бэкендов constrained decoding
на этом отдаёт 400. Если проба §1 упала с 400 — сначала плоская
схема (`type: ["string","null"]`), если не помогло —
`LLM_STRUCTURED_MODE=tool`. **Результат:** проба §1 не упала на 400
ни разу (три живых прогона, см. «Результаты пробы» п.1) —
Together/DeepSeek V4 Pro принимает `response_format` с
`anyOf`/`$defs` от Pydantic без `strict`. Лестница не понадобилась;
`LLM_STRUCTURED_MODE=tool` всё равно проверен отдельно (чек-лист §6
п.3) и работает так же, оставлен как задокументированный фоллбек в
таблице ниже, не как основной режим.

## Вердикт по критериям приёмки §2

| Критерий (ТЗ §2) | Порог | Факт | Статус |
| :---- | :---- | :---- | :---- |
| `structured(ObservationOut)` — валидный JSON с 1-го раза | ≥ 2 из 3 | 2 из 3 (`response_format`), 2 из 3 (`tool`) | ✅ пройден |
| `skill_id` только из переданного списка | все | все, в обоих режимах | ✅ пройден |
| `stream()` — инструмент вызывается, текст после него | вызван + есть текст | вызван, текст есть (через продолжение потока) | ✅ пройден |
| `stream()` — время до 1-го `text_delta` | < 3 с | 12.98 с / 14.59 с | ❌ не пройден |
| Лимиты аккаунта с датой и источником | известны | не проверено (нет доступа к дашборду) | ⚠️ открыто |

Решение по провайдеру и слотам (Together AI, V4-Flash/V4-Pro) остаётся
в силе — structured-output критерий, ради которого он принимался,
пройден с запасом. Непройденный критерий времени до первого токена
относится конкретно к сценарию «стриминг с инструментом» на `chat`
и в Ф1 не блокирует приёмку (эхо-режим `router.run_chat` инструменты
не передаёт, см. «Результаты пробы» п.2) — зафиксирован как открытый
риск на Ф2 (`run_tool_loop` тутора). Лимиты аккаунта — открытый пункт,
не блокирует эту фазу технически (`LLM_RPM_*` стоят на консервативной
заглушке `10`), но должен быть закрыт до продакшен-трафика.

## Пересмотр

Решение действует на Ф1–Ф3. Пересматривается, если проба §1 не
набирает 2 из 3 ни на одной модели каталога, или если расход
превысит половину остатка на ключе до начала Ф3.

## Расход на фазу 2

Оценка — до прогона `scripts/gen_templates.py`, по прайсу `MODEL_BULK`
(DeepSeek V4 Pro 0813, $1.32 / $3.96 за 1M токенов вход/выход, таблица
«Кандидаты» выше) и по размеру промпта/схемы, не по факту.

**Число вызовов.** Цель фазы — ~150 шаблонов ЕНТ (30-B2-phase2.md §3.2:
25 навыков × 2–3 шаблона). `gen_templates.py` шлёт один `structured()`
на навык с `--n` шаблонов за вызов; при `--n=3` по умолчанию это
⌈150 / 3⌉ = **50 вызовов**. Плюс запас на встроенный одиночный ретрай
`structured()` при невалидном JSON с первого раза — берём консервативно
10% вызовов ретраятся: 50 × 1.1 ≈ **55 оплаченных вызовов**.

**Токены на вызов.** Системный промпт `gen_template_v1.md` — 3487
символов шаблона (`len(text)` файла) плюс подставляемые блоки: формат
экзамена (2 секции ЕНТ, ~300–400 символов), заблуждения области
(2–4 записи с описанием, ~200–600 символов) и до двух примеров
существующих шаблонов как JSON (~800–1200 символов каждый, до ~2400
символов). Итого системный + короткое пользовательское сообщение —
порядка 6500–7500 символов, берём **7000 символов**. Кириллица и JSON
кодируются BPE-токенизатором плотнее латиницы — берём консервативную
оценку 1 токен ≈ 2.5 символа (не измерено токенизатором провайдера,
только прикидка по символам):

    вход ≈ 7000 / 2.5 ≈ 2800 токенов за вызов

Выход — `n=3` шаблона по схеме `TaskTemplateSpec` в JSON (образец в
`docs/data-formats.md` §4 — один шаблон с отступами ≈ 800–1000
символов ≈ 350 токенов при том же коэффициенте) плюс скрытые токены
рассуждения `MODEL_BULK` (`LLM_REASONING_BULK=high`, «Что не работает»
выше: рассуждение клиент выбрасывает из `text`, но провайдер их
генерирует и биллит как output — не наблюдалось напрямую, берём
консервативно ~2000 токенов на задачу такой сложности):

    выход ≈ 3 × 350 (JSON) + 2000 (рассуждение) ≈ 3050 токенов за вызов

**Итог.**

    цена вызова ≈ 2800 × $1.32/1e6 + 3050 × $3.96/1e6
                ≈ $0.0037 + $0.0121 ≈ $0.0158

    55 вызовов × $0.0158 ≈ $0.87

Порядок величины — **около одного доллара** на весь прогон
~150 шаблонов ЕНТ. Ручная проверка по чек-листу (product-logic §5.4)
токенов не расходует — она читает уже сгенерированный JSON глазами,
не через модель. Оценка грубая (коэффициент символ→токен не измерен
токенизатором провайдера, доля токенов рассуждения — не измерена):
если фактический расход выйдет на порядок выше этой оценки — повод
остановиться и проверить промпт, а не списывать на погрешность.

**Фактический расход (первый живой прогон, ЕНТ alg, 5 навыков, 2026-09-18):**
11 вызовов `LLMClient.structured` (`MODEL_BULK`) — 2 в первом прогоне (упал на баге валидатора, см. `docs/tz/phase2/checklists/templates-ent.md`), 3 на добор трёх навыков, 5 на две перегенерации `ent.alg.inequalities` после калибровки промпта и 1 на добор `math.alg.linear_eq`, плюс 2 диагностических вызова вне скрипта (тем же промптом, для отладки причины отбраковки). `structured()` не отдаёт `usage` наружу (в отличие от `complete()`/`stream()`), поэтому точные токены не измерены; по оценке за вызов выше (§«Расход на фазу 2», ≈$0.0158/вызов) — порядок величины **≈$0.17** на все 11 вызовов, в пределах оценки на порядок.
